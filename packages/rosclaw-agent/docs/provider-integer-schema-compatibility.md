# Provider integer schema compatibility

Materialized tool parameters are an immutable provider-facing copy of the capability input schema. For schemas declaring `integer` (including type unions), unsafe numeric minimum/maximum/exclusiveMinimum/exclusiveMaximum are omitted, not clamped. Safe bounds remain unchanged, including fractional minimum 1.5 / maximum 5.5 and exclusive +/-0.5 on integer or integer/null schemas. Unsafe means an integer-valued numeric bound outside Number's safe integer range, not every noninteger number.

Inherited-type projection is conservatively unsupported: a schema-position node with no local `type` and an unsafe integer-valued numeric bound throws an Error with code and readable prefix `PROVIDER_SCHEMA_UNSUPPORTED` before tool materialization returns or provider dispatch. This includes bounds in nested/multi-level allOf, sibling type declarations and referenced definitions. We do not resolve inherited types or claim success for rejected capabilities. This can also reject type-less bounds inherited from number schemas; locally declared number schemas retain their numeric bounds unchanged. Safe inherited bounds remain copied unchanged. No unsafe inherited bounds are silently advertised, and no integer domain is narrowed to MAX_SAFE_INTEGER. Schema positions in objects, arrays, definitions, dependencies and combinators are recursively projected; annotations, enum/default/const data, refs, required and additionalProperties remain intact. References remain references; local definitions are projected. External schema resolution is not added.

The provider projection deliberately relaxes only schema hints. The canonical Python/backend domain remains signed int64, including legitimate modern epoch nanoseconds above Number.MAX_SAFE_INTEGER. Backend validation remains authoritative, rejecting below -9223372036854775808 and above 9223372036854775807. No Python schemas or backend validators are changed. Capability ID, snapshot digest and direct/propose/internal routing remain unchanged; execute forwards the original params object, without timestamp conversion or clamping.

JavaScript Number cannot exactly represent arbitrary epoch nanoseconds. The parsed positive int64 bound rounds to 9223372036854776000, beyond signed int64. Removing unsafe schema bounds avoids advertising that rounded bound; it does not recover precision already lost during JSON parsing. This repair does not introduce BigInt wire encoding, strings, or claim end-to-end exact nanoseconds from Number. Tests use BigInt for exact contract arithmetic (not a backend integration test), and verify unchanged Number argument forwarding. The public Python control independently checks the canonical boundary.

Validation is source-only: TypeScript compilation, current targeted/regression tests and independent local controls, no live provider or hardware. Root's historical filtered/safe-bound provider controls identify a trigger but are not current product acceptance. Root must separately run unfiltered 45-tool product provider validation; source-only exact-name operator filtering is not a product change or completion gate.

No writer, Mission lifecycle, lease, SDK or OS-sandbox guarantees are implemented here. A protected Mission lease is not JSONL file exclusion; neither path is tested by this schema repair. Budget contract: LOW 600 seconds total / 570 source / 30 cleanup, zero provider retry and feedback; aggregate output 65536 is observable post-response cutoff, not a never-overrun hard limit. Per-response limit is UNKNOWN_UNSUPPORTED_BY_CURRENT_SDK.
